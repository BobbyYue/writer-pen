# 维护时检验方法，不在每次写作中运行测试集

## 程序检查

覆盖维护还运行 `test_review_coverage.py` 与 `test_native_coverage.py`：逐项删除必答项、
伪造旧稿引文、保留存疑写法却不做比较、跨稿丢失旧问题、仅用标题充当开头，以及作者自查覆盖缺项，
都应在对应入口被拒绝。正例须允许有依据的短段、无题、静态散文与无修改需要，不靠强制重写取得通过。
维护覆盖项时只改 [共用清单](review-coverage.md) 并验证分发、模板、返回校验同步；
不要分别维护三份列表，也不把任意新写作建议自动升级为强制审美规则。

在skill目录执行：

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

测试顺序、版本失效、引文定位、问题处理、明确约束、原稿保护和交付一致性。
`test_lifecycle_guard.py`实际运行共享引擎，覆盖缺关联/阶段、错profile、旧稿/旧评审、隔离packet和三轮后当前稿未通过的草稿导出，
包含早先版本通过、当前版本回归的情况；不以历史pass代替当前评审，也不要求历史全部fail。
成功路径使用`lifecycle_fixture.py`的合成过程记录，不是真实独立审稿，也不作为文学效果提升证据；没有mock掉交付校验。
还要运行skill-creator自带的quick_validate.py；该程序只检查技能元数据与脚手架，不检查文学行为。
不要让测试只匹配“已检查”字样、某个标题或评分表。构造破坏条件与正常条件，观察真实结果和错误状态。

## HTML维护

HTML维护同时运行`test_html_output.py`：合成材料验证题名、字词、段序、分段、转义、
多版本、不可覆盖、资源与锚点，以及HTML绑定已有审读、改版失效和未完成阻塞。
成功的受管流程用合成记录测试接口，不是真实文学审读；桌面/手机/无JS/打印还须在真实浏览器验证。
测试模板应包含长题名、长链接、段内换行及多个版本，不把静态通过代替页面效果。

## 正文行为测试

固定材料在 [behavior_cases.json](../tests/behavior_cases.json)，都是合成材料，不是用户私稿或名家原句。
每次把case的prompt和当前skill位置交给新的执行会话；**不把expectations或原有答案交给执行者**。
expectations供结果审阅者判断，描述应识别的关系和应保留的自由，不规定唯一成稿或唯一措辞。

## 完整写作回放

[workflow-cases.json](../evals/workflow-cases.json) 用于从素材到HTML的实际创作回放，
以及审读后的单独呈现更新；observe只给结果审阅者，不送给创作者。一次只发一项真实请求与skill路径，
在新的私有工作目录执行，使用统一入口、固定运行版本和真实专业/读者调用，不用fixture代替实际审读。
保留实际输入、封存时间、版本摘要、角色原始返回、编辑取舍、页面证据与最终文件。
若失败就记录停在哪一步，不补造成功；正常成稿、明确约束失败、审美分歧和呈现重查分别报告。
真实浏览器检查后仍须查看截图；文学效果请真实读者盲读校准。单次模型回放不证明稳健性或人类偏好提升。

程序测试包括统一入口、运行版本固定、方法实际分发、编辑取舍与呈现更新的正反路径。
这些合成记录测试只证明接口与保护条件；不能拿测试数量替代上述真实创作回放。

[阅读效果案例](../evals/reading-effect-cases.json)另外覆盖关系经历写薄、物件结尾的注意力转移、喜剧口气被磨平，
以及不应误改的充分铺垫、直接情绪和平缓开放写法。只把prompt和skill路径给执行者，
observations留给审阅者；逐项记录实际运行范围，不把新增案例文件等同于行为已经通过。
`test_reading_effect.py`只检查写作依据分离、读者两类回答、问题绑定、试改文字及旧稿失效，
不通过匹配特定结论或强制情感反应证明作品写得好。

[素材取舍案例](../evals/material-adaptation-cases.json)覆盖素材结论缺少发展、可以理解的误判、喜剧夸张、明确保留要求、
静态散文和非虚构边界。专业结果的 `development_response` 检查是否真正返回及引用绑定，不替代这些语义行为观察。
作者与专业包接收共用取舍准则，读者仍只读正文，不给其“应该发现心理跳跃”等定向答案。

[场景与行动案例](../evals/continuity-cases.json)覆盖换场缺口、愿望与行动脱节、局部修改后的状态连锁，
以及明确倒叙、可理解的矛盾和静态散文的正常反例。既查漏检，也查是否为了“连贯”误补所有路线、把矛盾人物修成理性人物。
两项审读记录、来源归属完整格式和大返回保全分别由程序测试核对；任何一项通过都不替代真实稿件审读。

[人物处境与判断空间案例](../evals/character-perspective-cases.json)覆盖纯文学和创意文案中的不同价值排序、
有偏见的叙述声音、完整人物说唱段落及没有统一判词的叙事；同时以明确事实、人物误判和用户指定讽刺作正常反例，
防止把“不代读者选择”误做成所有事实相对、双方同对或人物中立。仍只给执行者 prompt 和 skill 路径，
不预置人物结论；读者可以理解人物却不认同，也可以得出不同判断，不以站同一边验收。未运行的案例明确记未运行。
变更共用准则和精简覆盖说明时，核对原有方法分发将其送入作者与专业包；检查精确选段和来源摘要，不能只看 SKILL.md 已写过这条原则。

[段落表现与信息量案例](../evals/creative-density-cases.json)专查创意文案里的材料丰富却写薄、典故只剩专名、
逐句质问反驳挤掉人物表现，以及连续经历和跨段呼应；以用户指定正式辩论、极短文案、无新增事件的有效留白和有限纪实事实作对照。
评阅者逐段指出稿件实际用了什么、增加哪一面理解、哪里仅是同义复述；不统计典故数后直接判好坏，不要求每行新事件。
仅给执行者单个 prompt 与 skill 路径，不能把本次“应该去辩论化”等修复目标或观察要点作为额外提示。
分别记录人物、信息分量、可理解性和文字节奏，不让其中一项改善掩盖另一项变差；没有音频仍不声称实际试唱。
一次合成试写只证明该输入上的行为，不代表其他文体、典故领域或真实听众已经通过；未执行案例照实保留未运行状态。

同一文件中的人物声音案例检查共同目标下的多人物陈述、不同岗位套用同一提纲，以及明确要求的共同格式、相近口气和清醒理性的有效台词。
先只给当前稿与中性问题，记录读者实际感到的说话姿态、关系及文字依据，再对照写前材料；不把人物说明送给读者帮正文补性格。
比较旧版与新版时保持单个请求和材料相同，执行者只收该 prompt 与相应 skill 路径；评阅者不知道版本身份，允许两者同样薄或各有得失。
换人比较只作语义诊断，不用姓名猜中率、口头禅数量、结构相异率或人为添加的缺点数自动判好；用户指定的相同结构须保留。
实际试写与正常反例分别记录，未运行不能记通过；没有成对结果或真人反馈时不声称新版更好或已稳定解决人物同质化。

其中的补充取舍案例另查能力覆盖完整却压平人物、解释重复已成立的行动，以及新增履历打断情绪落点；以必要前提、人物有意邀功和明确要求的完整述职作正常反例。比较实际讲法与新增材料的得失，不以删字数、去解释词或添加缺点判优；不把这些创意台词案例扩成业务报告的通用删减规则。

拟题与题文复核用 [title-cases.json](../tests/title-cases.json)，覆盖有效原题、题文误导、有限材料、
不同方向的候选、只改题不动正文、有意预告、长题和非文学标题边界。仍只把prompt与skill路径给执行者，
不能把预期答案、全部案例或修复思路交给它。逐个独立运行；不把几个标题生成得顺口算作整体回归通过。
标题与正文同版本的机械核验沿用现有稿件绑定测试；行为观察不替代真实读者对文学效果的判断。

检验默认写作流程时，用没有额外要求拟题的完整创作请求，观察是否在起草前留下工作标题、
成稿后依据当前全文决定保留或修改，并将题名与正文一起送审。仅最终稿有标题不证明写前已拟题。
再用固定题名、明确无题、只要正文和仅改标题作对照，检查默认步骤没有覆盖用户范围。
未实际运行这些创作请求时，只能报告规则一致性检查，不能称为写作行为已验证。

维护者在任务目录保留case_id、skill版本/文件摘要、实际模型配置、执行日期、重复编号、完整回答及审阅结果。
未知的模型设置记未知，不编版本。不要把真实作品自动收进回归集；新增案例须合成或另获授权。

- **重复**：优先在关键案例上独立执行多次，例如先做两次探索；报告每次结果与分母，不能把一次成功叫稳健。
- **成对**：包含缺铺垫与有铺垫、信息提前与合理获知、必要删减与误删。人物反应还要比较支撑不足的具体筹划、积累充分的强烈情绪、已建立的喜剧夸张和素材夸张的写实展开。既看漏检，也看误报和修坏。
- **对照**：同一批材料比较旧版与新版；让评价者不知道版本身份，交换展示顺序，允许持平、各有所长和无法判断。
- **留出**：调试用案例与用于最终验收的新案例分开；在调试题上变好不等于泛化。风格、文体与长度不能只覆盖一类。
- **校准**：重要审美结论请用户或真实读者复核；模型之间一致不等于人类认同。抽查引文是否支持结论及被忽略的反例。

分别报告：流程遗漏、明确约束违背、漏检、误报、被修坏的有效表达、版本偏好分歧和实际时间成本。
有明确标注的案例才能统计相应比例，给出分母；不能把所有“不喜欢”都统计成错误，不合成文学总分。
少量样本只作行为观察，不声称统计上证明质量提升。

## 什么时候更新

修复应由可重现问题或真实使用反馈驱动。先复现，再改最小范围，并重跑相关案例及正常反例。
新增强制检查前确认：是否确有读者损失、是否已被既有检查覆盖、能否触发式执行、会不会误伤其他风格。
发布前分别核对规则文件、程序测试、行为结果、实际安装副本；任一层通过不代表其他层通过。

这里的版本比较、重复执行与人工校准参考 [OpenAI评估指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，
过程记录与结果评估的区分参考 [工作流评估说明](https://developers.openai.com/api/docs/guides/agent-evals)（本次核对日期2026-10-19）。
这是本包的本地测试方法，不依赖某个在线评估服务，也不把官方通用建议视为文学效果实证。
